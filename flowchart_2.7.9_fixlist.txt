MAJOR

1. Merge-splitter creates duplicate or wrong steps and an endless coverage loop (worst flowchart bug).
   Problem: duplicate boxes. QC: "Show order confirmation & est. delivery time" x2, plus "Show est. delivery
   time", "Send confirmation SMS and email" + "Send confirmation email", "Show login" + "Show login /
   register", "Show changes & ask user to confirm" + "Ask user to confirm changes". FM: a second
   "Escalate to HR manager" inserted between Submit and the 3-day decision, so escalation becomes
   unconditional.
   Evidence: QC trace step 9 coverage_check "Merged activities in one task 'Send confirmation SMS and email'
   — split into: 'Show order confirmation & est. delivery time', 'Send confirmation SMS and email'" and
   "'Show order confirmation & est. delivery time' — split into: 'Show login / register', 'Show 'Cart is
   empty'', 'Show changes & ask user to confirm'". The draft already had n_split_1/n_split_2 (QC's own
   recommendation names them). All 4 QC LLM verdicts said "approved / all steps covered", yet the pipeline
   forced revisions because of this gap. Revisions 1 and 2 returned 33/39 again, and revision 3 jumped to
   37/43 by adding a2_no_login, a5_yes_confirm, a20_eta and a21_email: the generator "split" exactly the
   labels the gap text told it to. FM trace steps 9-29: the same gap 4 times, and the QC LLM blocked the
   n_split_2 that the repair kept re-inserting.
   Root cause: app/services/process_coverage.py
     - _verb_stems (~413-428) treats any token of 4+ chars as a "verb" (show, confirmation, manager, send,
       deliver, time…). _GENERIC_STEMS misses these.
     - _merged_activity_gaps (~431-448): any process label containing "and"/"&" whose stems overlap 2+
       inventory activities counts as a gap. This includes the node's OWN correct activity, e.g. "Send
       confirmation SMS and email" is itself an inventory item.
     - repair_merged_process_nodes (~451-556) takes hits[0], hits[1] in inventory order, not the parts of the
       label. So it replaces "Send confirmation SMS and email" with ["Show order confirmation…" ->
       "Send confirmation SMS and email"]. The second label still contains "and", so the gap can never clear.
       The copy keeps type=process, which makes "Show order confirmation…" a process node and triggers a
       second gap. node_b sits at x+0.35w, y+24 (n_split_2 at x=592 off the spine).
     - Called after every draft and revision: diagram_pipeline.py:302-304, 345-347, 498-500.
     - The gap is merged as BLOCKING (diagram_pipeline.py:146-162 _merge_coverage_into_audit) and is added to
       the revision prompt twice (blocking_issues + coverage_revision_issues, :468-479).
   Fix:
     a) Remove repair_merged_process_nodes from the flowchart path. Gate it so it never runs for diagram_type
        == "flowchart", or delete it.
     b) _merged_activity_gaps: skip any node whose label matches one inventory activity with ratio >= 0.85.
        Split the label on " and " / "&" and require each PART to match a DIFFERENT inventory activity.
        Never count the node's own activity. Make it ADVISORY (trace only) for flowchart, never blocking.
     c) No-progress guard in the revision loop (diagram_pipeline.py:454): if the blocking set is identical
        to the previous round (same coverage gaps), stop and return the best draft. Never spend 3 rounds
        on an identical gap.
     d) When the QC LLM says approved and only deterministic coverage items remain, run at most 1
        revision, and only for "Missing activity/decision/branch" gaps, not "Merged…".
     e) Add coverage gaps to the revision prompt once, not twice.
   Acceptance: QC prompt → 0 nodes with id n_split_*, no two nodes with the same normalized label, exactly one
   "Show order confirmation…" and one "Send confirmation SMS and email", no "Show login"/"Ask user to
   confirm" extras, revisions <= 1. FM → exactly one "Escalate to HR manager", only on the d3 No branch;
   Submit → d3 directly.

2. Planner crashes on flowchart I/O and fork kinds (wasted 12–42 s, then coverage silently skipped).
   Evidence: FS process_plan_skip "elements.1.kind Input should be 'start','end','activity' or 'decision'
   [input_value='input']" (12.1 s wasted). FX: "input_value='gateway'" (42.0 s wasted).
   Root cause: app/schemas/process_model.py ProcessElement.kind = Literal["start","end","activity","decision"].
   The model naturally emits input/output/gateway/fork/join for flowcharts. The planner example in
   app/prompts/process_plan.py also shows "Place Order & Pay" as one activity, which teaches merged labels.
   Fix: accept the kinds and map them with a pydantic field validator before the Literal check:
   input/output/io/display/document → activity; gateway/xor/fork/join/parallel → decision (or a new
   "parallel" kind that coverage ignores). Change the example label to "Place Order".
   Acceptance: FS and FX logs show process_plan_ready (no process_plan_skip) and the inventory counts match
   the brief.

3. Speed. QuickBite took 62.7 s chat + 266.7 s generation, and attempt 1 timed out at the 540 s abort.
   Evidence: timing table above; 60% of QC's time is the 3 pointless revisions from #1.
   Contributing causes:
     - Revision loop driven by an unsatisfiable deterministic gap (#1). It always burns max_qc_revisions=3.
     - Every revision regenerates the FULL diagram JSON with coordinates (~45–66 s each on gemini-4-argon)
       instead of a patch.
     - The planner runs SERIALLY before the generator (21–42 s), even though its inventory is only needed
       for the coverage check. The analyst brief already lists every step.
     - app/services/gemini_client.py:31-41 _thinking_config only sets thinking_level when the model name
       contains "gemini-3"/"*-latest". gemini-4-argon (the live generator, planner and analyst) gets NO
       thinking config, so the model default applies and the "low" levels for analyst/planner are ignored.
       Likely a big share of the 30–66 s calls and of the 62.7 s chat; confirm via the logged
       thoughts_tokens.
     - ai.timeout_seconds is a soft timeout only (gemini_client.py:86 only logs after the call returns).
       There is no real per-call or pipeline deadline.
   Timeout chain (attempt 1, about 10 min end to end, null result, empty canvas): the frontend abort
   static/js/designer/app.js:1388 `const timeoutMs = 540000` fired first. nginx proxy_read_timeout is 600 s
   (deploy/nginx-dd-root.conf:18), but the NDJSON trace lines reset it between events, so nginx rarely fires.
   uvicorn (deploy/genai.service ExecStart) has no request timeout. The worker thread in app/main.py:260-270
   keeps running after the client aborts, so Gemini calls are wasted and load stacks up for the next request.
   sendRequirementsMessage (app.js ~705) has no timeout at all.
   Fix:
     a) Fixes 1–2 (removes ~160 s on QC and ~125 s on FM).
     b) Treat every gemini-* model as thinking-capable. Map role to thinking_level for any family that
        supports it, and fall back gracefully if the SDK rejects it. Log the latency per call in the trace
        (add "took Xs, model, thoughts_tokens" to each agent trace detail).
     c) Run the planner concurrently with the first generator draft (ThreadPoolExecutor). For flowchart, do
        not inject the inventory into the generator prompt. Use it only for coverage. Optionally run the
        planner on the fallback flash model.
     d) Server-side pipeline budget (e.g. 240 s). Skip further revisions when the budget is spent and return
        the best draft with a "partial" note. Pass a real http timeout to the genai client
        (HttpOptions(timeout=...)) = ai.timeout_seconds.
     e) Stop the worker on client disconnect: check `await request.is_disconnected()` in the stream loop and
        set a cancel flag that the pipeline checks between steps.
     f) Revisions for flowchart: send the issues plus the current JSON and ask for a minimal patch (or at
        least a "keep all unchanged nodes" instruction), at revision_temperature.
   Speed targets (live, this exact set of prompts):
     QuickBite 4_flowchart.txt: generation <= 90 s (stretch 60 s), chat <= 20 s, never a timeout in 5 runs
     fc_simple <= 40 s | fc_medium <= 60 s | fc_complex <= 120 s | edit <= 40 s
     Revisions: 0–1 on all four; never the same gap twice.

4. Edit-mode merge restores old positions, so new shapes overlap.
   Evidence: QCe canvas JSON: the server moved d15 "Cash on Delivery?" to y=2310 and a15_no to 2338 to make room,
   but on the canvas they are back at y=2200/2228, overlapping the new d_gc "Gift Card selected?" (2150–2260)
   and a_gc_val (2173). Programmatic overlap check: 2 overlaps (screenshot ours_4_flowchart_edit.png).
   Root cause: static/js/designer/app.js:1512-1538 mergeEditPreserveLayout. Lines 1522-1535 restore
   old.x/old.y whenever the size didn't change by more than 8 px and the prompt has no geometry verb. They ignore
   that the server deliberately shifted the node.
   Fix: keep old positions only if the server position equals the old one (|dx|,|dy| <= 8), or if the node would not
   overlap any NEW node. Otherwise accept the server position. After merging, run an overlap pass (same as
   _layout_flowchart_space) on the client, or skip the client merge entirely when the server reports
   edit_mode layout. Optional: the server returns meta.moved=true on shifted nodes.
   Acceptance: rerun the edit → 0 bounding-box overlaps; all 37 original ids kept; labels unchanged except
   a14; nodes above the insertion point keep exact x/y.

6. Flowchart layout and routing: hook loops, LLM coordinates, label placement, Fit clipping.
   6a Hook-shaped "loops" on forward edges. Evidence: the small loops left of "Any item unavailable?",
      "Create order record", "Calculate subtotal" (QC); "Underwriter approves? Yes → Calculate…" and
      "Pull credit score → Join" (FX); both failure exits in FS. Root cause:
      static/js/designer/canvas.js:1209-1271 _routedEdgePath, line ~1218:
      `isLoop = y2 + 8 < y1 || (x2 + 40 < x1 && Math.abs(y2 - y1) > 20)`. Any edge whose target is
      slightly higher (d5 → a5_yes: target y 660 vs decision 680) or anywhere down-LEFT (d16 → a19) is treated
      as a loop-back. It then goes out the bottom, around a left gutter and back in from the left, sometimes through
      its own source. Fix: decide loop-ness from the GRAPH, not from geometry. Do a DFS from the start terminator,
      flag back-edges (server sets edge.meta.back_edge=true in the normalizer, the client falls back to its own
      DFS), and use the gutter route only for real back-edges. Forward down-left edges use a simple
      vertical→horizontal elbow.
   6b Coordinates come from the LLM and nobody lays them out. Evidence: FM flows upward and across 4 columns
      (d3 above Submit; "Manager/HR approves?" above both). QC is 3614 px tall with ~140 px row steps.
      edge.meta.waypoints that the generator spends tokens on are IGNORED by canvas.js (no reference to
      "waypoints" anywhere in static/js). diagram_normalizer.py:697-728 _layout_flowchart_space only nudges
      overlaps. Fix: add a deterministic layered layout for flowchart in the normalizer (Sugiyama-lite:
      ranks by longest path over forward edges; the main spine follows the Yes / unlabeled successor; No
      branches and side activities go in the column to the right; End terminators of failure branches sit
      to the right of their decision; back-edges use the left gutter; row gap ~100 px, column gap ~260 px).
      Then drop the coordinate and waypoint instructions from the flowchart generator prompt
      (app/prompts/diagrams.py:159-167 and :222). Fewer output tokens also means faster generation.
      Also remove "y:40–1200" (diagrams.py:167): the QC LLM turned it into a BLOCKING issue in FM rev 2
      ("coordinates exceed y: 40–1200").
   6c Branch labels far from the decision. Root cause: canvas.js:1075-1108 _labelAnchor puts the label on the
      LONGEST segment (FX "Yes" mid-way to Fork, QC "Yes" halfway down the COD spine). Fix: for edges from a
      decision, anchor the label on the first segment, ~16 px from the exit point.
   6d Fit View clips tall flowcharts. Evidence: ours_4_flowchart.png cuts "Start" at the top and "End: Order
      placed" at the bottom. Root cause: canvas.js:39 MIN_ZOOM 0.25, applied in fitToContent (:647). 3614 px ×
      0.25 = 903 px is taller than the ~760 px usable canvas. Fix: let fitToContent go below MIN_ZOOM (fit-only floor,
      e.g. 0.1). The compact layout from 6b mostly removes the need.
   6e Fork/Join drawn as 40 px "connector_node" dots with the words Fork/Join (FX). Fix: add a flat
      "parallel bar" render for connector_node when it is labelled Fork/Join, or teach the generator to use
      preparation/bar.
   6f FS merged both failure exits ("If this email exists…" and "Link expired") into the success End "Password
      reset complete". Fix: a generator flowchart rule plus a coverage check: a branch that "→ End" after an
      error gets its own End terminator unless the brief names the same end.
   Acceptance for 6: on all 4 prompts, 0 hook loops on forward edges, every back-edge drawn in the gutter, no
   edge segment through a non-endpoint node, every Yes/No label within 40 px of its decision, Fit shows
   Start and every End fully, main spine top-to-bottom (no node ranked above its predecessor except on
   back-edges), height for QuickBite <= ~2600 px.
